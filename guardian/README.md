# Customer onboarding and acceptance

## Prepare the customer environment

Use an existing private versioned S3 bucket in one AWS commercial Region and select a prefix ending in a slash. AEGIS deploys its own connection resources alongside that bucket. The application that writes customer files is independent.

1. Choose the customer's AWS account, Region, versioned bucket and authorized prefix. Generate a unique external ID for the deployment with `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`. The runtime role and customer trust policies use this value for short-lived STS sessions.
2. Generate the stack with `python3 guardian/template.py > guardian-template.json`. Deploy it in the source bucket's account and Region. Supply the exact provider role ARN and external ID. The default **DedicatedTrail** creates a separate logging trail and retained log bucket. It records writes under the protected prefix and reads under its reserved `.aegis-canaries/` directory. Set **LegacyCanarySuffix** to an existing decoy's key relative to the prefix to capture reads on that key. The stack owns its event selectors and preserves the customer's existing trails. Customers who supply equivalent logging can select **DedicatedTrail=disabled**. Review data event and storage costs before deployment. [CloudTrail data events](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html)
3. Enable **TestActions** only when enrolling the stack's dedicated sandbox TestWriter and ControlWriter. The responder manages one reserved inline policy on TestWriter. The control role can write synthetic probes. The monitor consumes SQS and checks bucket versioning. The separate setup role creates and checks versioned canaries. Recovery has its own role and destination.
4. Allow the Aegis runtime to assume only these deployment roles. Copy `guardian/settings.example.json` to an operator settings file and enter the actual outputs, including `setup_role`. For an action rehearsal supply all of `action_role`, `test_role` and `control_role`. List business read-only actors and independently trusted recovery baselines if applicable. For KMS-encrypted storage, the customer must grant the relevant role and key permissions.
5. From `backend/`, run `alembic upgrade head`, then `python -m aegis.connect --customer demo --label "Customer reports" ../customer-settings.json`. The tenant administrator must exist. Registration reserves the queue and external ID. For an existing binding, run the same command with `--upgrade-setup` after updating the stack. This attaches the dedicated setup role to the original connection.
6. As the customer administrator, open the registered deployment in **Connections**, check the account and scope, enable the connection and select **Provision three canaries**. The API can also activate an exact registered scope using `POST /api/v1/ops/connections/aws`. Three slots under the reserved canary prefix have durable setup intents. The setup role inspects version history and uses conditional creation. Repeating setup preserves completed baselines. A conflict identifies an occupied customer key. Setup allocates a fresh replacement under the reserved prefix and preserves the occupied object. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)
7. Select **Check read delivery**. A successful S3 read begins a check. The worker confirms the read when the corresponding CloudTrail event reaches SQS. Inspect each key's request, event ID and time in connection detail. If read logging is known to be unavailable, set `read_logging_available` to false in the operator settings. Queue health is reported separately. The worker tracks observed reads, overwrites and delete events, including individual object events delivered for bulk deletes.
8. Apply customer-approved rules through the [dashboard API](../docs/guardian-api.md). Automatic containment and the rolling bulk rule begin disabled. Each restriction has an expiry and can be reversed. Configure emergency role exemptions and approved UTC job schedules before opting in.

## Live rehearsal

Upload a small harmless revision of a synthetic object through the customer's normal upload path. In **Activity**, check the exact key, operation, owning connection and IAM actor. Compare the event and receipt timestamps in the evidence export. A green queue check alone is insufficient evidence that CloudTrail logging and delivery work.

For a canary rehearsal, upload a prepared harmless revision to the pre-existing synthetic decoy using the designated sandbox role. The case should explain which conditions were observed. A canary event or a rolling alert can qualify the enrolled writer for a scoped response. Other correlations require two signals. Review the proposed restriction and approve it in the console. The worker checks scoped writes by the test and control roles and records the outcome. If recovery is the only exercise, record the reason to skip containment.

Open a recovery preview and review every selected source version and destination. Approval expires after 15 minutes. The worker checks the currently observed version, verifies trusted source bytes, writes to a separate bucket with a conditional create, and verifies the stored bytes. Delete markers can serve as the observed revision. The trusted historical source must still be readable. An approved job can resume after a process restart by checking its deterministic destination. Downloaded cloud copies are pinned to the verified destination version.

For optional entropy sampling, list only designated synthetic keys under `synthetic_sample_keys`, each with a trusted baseline. Explicitly grant the monitoring role version-read permission for those keys. AEGIS compares up to 64 KiB per pinned version when the event contains a version ID. A missing sample leaves the remaining signals available.

## Integrations

Set `AEGIS_PUBLIC_URL` to the externally reachable authenticated console address. Supply connector secrets through the worker environment or an injected secret store. Configure each customer separately.

- **Slack.** Put the incoming webhook URL in a customer-specific environment variable such as `AEGIS_SLACK_DEMO`. Set `slack_env` in the customer settings to the name of that variable. The worker sends the incident reference, phase and console link. Failed deliveries have bounded retries. A remote acknowledgement lost during a worker crash can result in a repeated Slack message.
- **Jira Cloud.** Supply a `jira` object containing `host` (the customer's atlassian.net hostname), `project`, `issue_type_id`, `email` and `token_env` (for example `AEGIS_JIRA_DEMO`). Set that environment variable to the API token. The account needs issue search, create and edit permissions. AEGIS looks up an incident label and updates the matching issue description. An uncertain create is recorded for review. [Jira issue API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/)

Both delivery types are durable jobs visible in the incident. Connector failures are recorded separately from recovery outcomes. An administrator should reconcile uncertain deliveries with the external tool before another send.

## Failure handling and teardown

- **No events.** Check connection activation, worker health, trail scope, Region, EventBridge rule match and queue access. Inspect failed or malformed records in the dead-letter queue. The worker leaves unsuccessfully processed records on SQS for redelivery.
- **Missing evidence.** A role match is required for containment. Without a suitable source version and trusted digest, the affected object needs manual review. The optional rolling rule considers earlier and later event-time neighbors on late delivery. CloudTrail visibility and delivery latency determine when detection can begin.
- **Partial action.** Inspect per-file results and download only verified items. Prepare a new preview for unresolved files after correcting the prerequisite. For a failed containment verification, inspect the dedicated test policy, then preview reversal. Record customer policy changes before retrying.
- **Teardown.** Reverse all active test restrictions and verify both probe roles. Pause the connection, review any queued actions, preserve the case export and remove the AEGIS stack after the customer is ready. Check CloudTrail selectors and remove only the ones created for the exercise. The retained recovery bucket, source versions and decoy stay under customer control. Review them separately for retention and cost.

### Connect notifications to a replay workspace

A replay demo can exercise the notification adapters without an AWS account. Open **Connections**, copy the displayed connection ID. Prepare a small JSON file with the `slack_env` and/or `jira` fields described above. From the backend environment run `python -m aegis.integrations --customer demo --connection CONNECTION_ID integrations.json`. This updates the destinations for subsequent incidents. Both connectors use the worker environment. New replay connections start with external notifications off.
